# World and Offload Foundation Checkpoint - August 30, 2026

## Outcome

The testbed can run uncapped, synchronized to the active monitor, or at an explicit render cap while retaining its fixed 60 Hz simulation. It now has a bounded CPU job system, a GPU-driven background effect, and an EnTT-backed World with no EnTT types exposed to callers.

## Monitor and render pacing

- `--uncapped` selects unlocked presentation and remains the default.
- `--monitor-hz` or `--vsync` synchronizes presentation through the active monitor's VSync path.
- `--fps=N` applies an explicit software render cap.
- F6 cycles unlocked, monitor-synced, 60 Hz, 120 Hz, and 144 Hz modes while running.
- The current monitor reported 240 Hz during validation.
- The fixed gameplay tick remains 60 Hz in every presentation mode.

This changes engine presentation pacing. It does not modify Windows display settings or the monitor's configured refresh rate.

## CPU offload foundation

The `JobSystem` module provides:

- a bounded default worker count that leaves one logical thread available and caps itself at 16 workers;
- queued fire-and-join work;
- parallel range splitting;
- idle synchronization;
- worker-exception propagation to the waiting caller;
- clean worker shutdown.

The current machine initialized 15 workers. World structural mutation remains main-thread-owned. CPU jobs should initially consume immutable snapshots for asset decoding, procedural generation, pathfinding, or other independent work.

## GPU offload foundation

- The testbed grid is generated by a GLSL 330 fragment shader instead of CPU line submission.
- The shader compiled and linked successfully on the RTX 2080 Ti.
- G toggles between the GPU shader and a safe CPU-rendered fallback.
- Shader resources are released before the graphics context closes.

This is the first GPU workload seam, not a general GPU-compute system. Raylib/OpenGL resource creation and draw submission remain on the main thread.

## World module

- EnTT 4.0.0 is pinned as the private storage implementation.
- Callers use engine-owned `EntityId`, `Transform2D`, `Sprite2D`, and `RenderItem2D` types.
- Entity creation and destruction are deferred and applied in command order.
- Invalid entity access fails safely.
- Render snapshots are sorted by layer and stable entity ID.
- The player and blue crate visible in the testbed are World entities.
